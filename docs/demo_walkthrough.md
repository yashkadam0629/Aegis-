# Demo walkthrough, interview talk track and resume bullets

All figures below are **synthetic-benchmark results** produced by this repository (see `docs/evaluation_report.md`, regenerated by `python -m app.report`). Use the phrase "on a synthetic benchmark" whenever you quote them.

## A. Five-minute demo script

1. **Overview** – state the dataset banner ("SYNTHETIC DATA"), then hover the *Potentially exposed value* tooltip: distinct transactions once, only the largest hop for chains and cycles — "this is not a loss figure".
2. **Alert Center** – sort by risk. Open the top alert (a 5-hop circular flow that is also a pass-through chain). Show *Summary* (two detectors corroborating), *Evidence* (the five transactions), *Explanation* (noisy-OR family breakdown + SHAP bars + the "not a probability" caveat), and the *Data limitations*.
3. **Create investigation** from the alert; show it appears as `New` with the evidence attached; move to *In Review*; try to *Resolve* without a disposition and show the 409 validation message; add a note; show the audit trail.
4. **Network Explorer** – open from the alert ("Open in Network Explorer"): the cycle edges are highlighted in red over the neighbourhood. Click a node: stats, linked alerts, linked investigation. Use *Trace forward* and point out the "approximate flow tracing" warning. Show the truncation banner and explain bounded subgraph extraction.
5. **Network Intelligence** – communities (Louvain) with internal/external flow and highest-risk members; then *Shared beneficiaries* and point out a benign look-alike with a low score (baseline-aware concentration).
6. **Model Performance** – chronological split, feature-group comparison with bootstrap CIs, held-out templates, threshold table with *assumed* costs, calibration verdict ("score, not probability"), PSI drift with the caveat that drift ≠ accuracy loss. Business-impact tab: simple rules vs ML vs combined at fixed review capacity.
7. **Data Management** – show an import with rejected rows and the downloadable error report; mention untrusted-upload handling.

## B. How to explain it in an interview (90 seconds)

> "Transaction monitoring usually scores payments one at a time. I built AEGIS to also reason about *relationships*: funds that hop through accounts quickly while keeping most of their value, money that comes back around, many unrelated accounts converging on one beneficiary, groups paying the same uncommon payees at the same times. Each detector is time-aware and compares an account with its own history, so habitual hubs like merchants and payroll don't light up. A point-in-time feature engine feeds gradient-boosted models; evaluation is chronological with purged scenario boundaries, and I compare transaction-only, behavioural, graph and combined features. A small risk engine combines pattern, model and rule evidence without double-counting correlated signals and attaches evidence, exposure estimates and SHAP explanations to each alert. Analysts work cases with a state machine and an audit trail. Because the data is synthetic I describe results as benchmark recovery of simulated patterns, publish the failure modes, and refuse to call scores probabilities."

Likely questions:
* **Why not a GNN?** No evidence on this data that it beats interpretable local features; harder to explain to investigators; I listed it as a roadmap candidate after snapshot-embedding tests.
* **How do you avoid leakage?** As-of sweep (tested by truncating the future and comparing features), chronological splits, purging scenarios that straddle the cut-off, held-out template variants, labels stored in tables the inference code cannot import (tested).
* **What would break on real data?** Prevalence (~2.4% here), amount shortcuts, parametric scenarios, adaptive adversaries, label noise; detectors' thresholds need re-tuning; PostgreSQL/at-scale index not exercised.
* **Why is the graph model sometimes below the behavioural model on validation?** Small number of scenarios per period; the report prints validation and test orderings and says when they disagree.
* **How is exposure computed without double counting?** Per alert: distinct transactions once, largest hop for path patterns; across alerts: incremental unique value; never labelled loss.

## C. Resume bullets (only claims backed by results in this repository)

* Built AEGIS, a full-stack financial-crime analytics prototype (FastAPI, SQLAlchemy/Alembic, React/TypeScript, Cytoscape, ECharts) with ingestion + data-quality reporting, a temporal graph-detector library, a point-in-time feature engine, an ML pipeline, a risk/exposure engine and an audited investigation workflow; 63 automated backend tests and 7 frontend flow tests passing.
* Designed a leak-free evaluation (chronological split, scenario purging, held-out scenario templates, bootstrap CIs) on a deterministic synthetic generator with ten scenario families including benign look-alikes; on that synthetic benchmark a LightGBM model with behavioural + local-graph features reached test PR-AUC 0.93 vs 0.44 for transaction-only features and 0.10 for a rules baseline.
* Implemented temporal cycle / pass-through-chain / fan-in / coordination detectors that compare each entity with its own history and a time-shifted null; at fixed review capacity the combined prioritisation covered all 19 simulated suspicious scenarios within its top 25 alerts, though each alert bundles a whole pattern (326 transactions to read vs ~66 for transaction-level cases) — synthetic benchmark; assumptions and caveats documented.
* Engineered reproducible data tooling: incremental-vs-batch feature equality tests, streaming simulator reusing the batch feature state, and measured benchmarks at 10k / 100k / 500k transactions on a laptop-class CPU (see `benchmarks/results/`).

(Do not add claims about "fraud prevented", savings, real-world detection rates, PostgreSQL/Docker validation or Kafka — none were measured here.)
