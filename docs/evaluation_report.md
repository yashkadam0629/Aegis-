# Evaluation report

> **SYNTHETIC BENCHMARK.** Generated by `python -m app.report` from stored results of model run `MR-59202d67` (`D-lightgbm-20261024171619`) on dataset `DS-d8b2882d` (version `39b89a30b2a6`). Labels describe *simulated* scenarios, not real or legally established financial crime. Absolute numbers will not transfer to real data.

## 1. Dataset
- 72,384 transactions, 2,000 accounts, 2026-01-01 → 2026-04-30 (synthetic, seed 42).
- Positive (simulated-suspicious) transactions — train 973, validation 433, test 276. Prevalence is far higher than any real portfolio, so **precision values are not transferable**; ranking metrics at fixed capacity are more meaningful.
- Benign look-alike scenarios (payroll, marketplace settlements, group bills, recurring business transfers, seasonal merchants) are labelled *not suspicious*.

## 2. Evaluation design
- Chronological by timestamp. Training rows of scenarios extending past the training cut-off are purged. Features are strictly as-of each transaction.
- Train 2026-01-01 → 2026-03-13 (42,790 rows after purging 35); validation → 2026-03-31 (11,556); test → 2026-04-30 (17,989).
- Model selection rule: highest validation PR-AUC across all feature-group × algorithm combinations. Selected: **D_combined/lightgbm**.
- Features are point-in-time: computed from transactions strictly before each one (verified by a leakage test and an incremental-vs-brute-force equality test).
- Labels live in separate tables and are never read by inference, graph or risk code (enforced by a test).

## 5. Business-impact benchmark (cases, not transactions)

Evaluation window 2026-03-31 → 2026-04-30: **19 simulated suspicious scenarios**, 276 suspicious transactions. A *case* is a group of top-scoring transactions of one account within 24h (txn-level approaches) or one AEGIS alert. A case is a true positive if ≥50% of its transactions belong to a suspicious scenario; a scenario is detected if a true-positive case in the top-N contains one of its transactions.

**Read with care:** the case unit is not equally granular across approaches. An AEGIS alert bundles a whole pattern (several accounts and transactions), whereas a transaction-level case is a cluster of one account's top-scoring payments, so AEGIS reaches high scenario recall with few cases but asks the analyst to read more transactions per case (see the *Txns to inspect* column). Precision at N falls once the true cases are exhausted (the window holds only ~19 suspicious scenarios plus benign look-alikes), so P@100 mostly reflects how many true leads exist, not ranking quality.

Interpretation: the model degrades only slightly because simulated suspicious payments remain large and unusual in amount even when hops are slowed and value is leaked. Real adversaries would also adapt amounts; this test is a robustness probe, not a guarantee.

## 7. Limitations

- Labels are synthetic scenario labels; metrics measure recovery of simulated patterns, not real-world fraud detection.
- Synthetic prevalence (~2-3% of transactions) is far higher than real-world prevalence; precision is not transferable.
- Scenario templates are parametric; hold-out by template variant reduces but does not remove similarity between train and test patterns.
- Point-in-time graph features are local (bounded neighbourhood); global metrics such as PageRank/communities are not used in the supervised model to avoid look-ahead.
- Synthetic scenarios; templates are parametric so absolute numbers overstate real-world performance.
- Txn-level approaches are converted to cases by a simple grouping heuristic; a production queue would differ.
- Cost figures are assumed review costs, not measured savings; no fraud loss prevented is claimed.
- Evaluation window contains 19 suspicious scenarios; per-scenario recall has wide sampling uncertainty (each scenario ≈ 5.3 pp).
